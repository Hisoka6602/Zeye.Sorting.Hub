# Zeye Sorting Hub Web

来源：仓库内前端源码、Node 测试及本机设计验收记录；本文为项目原生说明，未从 doc/pdf 解析。

仓库根目录下的独立前端项目，目录名 `Zeye.Sorting.Hub.Web` 与现有 .NET 项目保持一致，npm 包名为 `zeye-sorting-hub-web`。按 `design/ant-design-blue-white` 中的 22 张蓝白主题设计图实现。技术栈为 React 19、TypeScript、Vite 和 Ant Design 5。普通运行模式的业务页面读取真实后端，失败时显示错误和重试入口。只读设计预览模式仍提供独立视觉样本。

## 启动

```powershell
cd D:\WorkSpace\Zeye\Zeye.Sorting.Hub\Zeye.Sorting.Hub.Web
npm ci
npm run dev
```

默认打开 `http://127.0.0.1:4173`。开发代理默认连接Host的 `http://127.0.0.1:5078`；可在启动前设置 `$env:ZEYE_API_PROXY='http://127.0.0.1:5098'` 覆盖。内置登录使用同源 Cookie；部署使用同源反向代理，开发代理同时转发 `/api` 和 `/health`。构建使用 `npm run build`，产物位于 `dist/`；客户端测试使用 `npm test`。

需要对照静态参考图时，可单独启动只读设计预览：

```powershell
npm run dev -- --mode design-preview --port 4186
```

打开 `http://127.0.0.1:4186`。P02、P03、P05、P18在此模式显示参考图的2026-09-25样本，P03路径为 `/parcels/2509250005`。台账筛选、详情链接、面包屑、报表筛选仍可操作；提交动作不会写入后端。普通 `npm run dev` 和 `npm run build` 继续读取真实API，不会用样本替换请求失败状态。设计预览仅供视觉验收，不能作为运营数据。

## 数字显示

界面数值通过 `src/data/formatNumber.ts` 统一使用定点表示：四舍五入后最多两位小数，去除末尾零，整数不补小数位。件数保留原有千位分隔，趋势图保留 K/M/B 缩写。输入期间保留编辑原文，结束编辑后使用相同显示规则。此规则只作用于显示；计算、规则比较、提交合同与原始 JSON 报文保持原有精度，条码及字符串编号保持原文。

## 项目结构

登录用户可从右上角账号菜单进入个人中心，修改名称、头像、邮箱、联系电话和个人简介。JPG/PNG 头像在浏览器居中裁剪，保存后同步显示到顶部栏；资料与头像保存在数据库中，刷新和重新登录后保留。普通用户可维护自己的资料，登录账号与角色只读；即使关闭全平台权限保护，个人中心仍需登录。

- `src/app`：路由、统一菜单和面包屑、共用母版、Ant Design 主题。`Shell.tsx` 与 `shell.css` 统一管理母版。
- `src/components`：可在多个业务页面复用的控件。
- `src/features/<业务域>`：业务页面及仅供该业务域使用的组件；每个页面单独按路由加载。
- `src/data/api`：统一请求客户端及包裹接口合同。
- `src/data/mock`：按业务域拆分的演示数据。
- `src/data/stores`：按业务域拆分的本地持久化状态。
- `src/app/shell.css`：固定侧栏、顶部栏及面包屑的共用蓝白样式。
- `src/styles.css`：各业务页面内容样式。
- `qa/current/`：本机生成的全站浏览器截图基线；之后调整的页面截图保存在本机 `qa/candidates/`。截图和构建产物不进入版本库。
- `设计验收.md`：逐页对照、修改历史、已验证交互与剩余差异。

新增页面时，将页面放入对应的 `src/features/<业务域>`，在 `src/app/App.tsx` 中配置路由；跨页面复用的展示控件放入 `src/components`。新页面共用 AppShell，只添加内容区；菜单与可点击面包屑统一在 navigation.tsx 配置，母版样式集中在 shell.css。接入后端时，可在对应业务域下增加 API 模块，避免把请求逻辑写入通用控件。

包裹列表、详情及写操作通过 `src/data/api` 请求真实后端，服务异常会明确显示错误，不回退演示数据。分析报表请求 `/api/parcels/analytics`，按首次入库日期展示来源包裹当前快照，并另列按事件发生日统计的失败尝试和未绑定DWS事实；最多查询31天。无有效生命周期样本时显示“—”，不伪造零秒平均值。新建包裹使用完整管理端新增合同；来源检测登记另有独立路由，其 `RecordId` 由来源实例、运行批次和来源包裹号确定性生成，重载页面后重试仍使用同一身份。批量导入使用完整 `ParcelCreateRequest` 合同，JSON及简单CSV均保留64位编号；入队响应不代表落库完成。清理结果完全由服务端隔离器决定。审计、慢查询、健康检查、归档、实时态势均读取服务器数据；归档提交和失败任务重试使用真实写接口。内置登录、账号和角色权限保存在数据库中，权限停用和账号停用会撤销会话。旧浏览器演示草稿仍保留在原 localStorage 中，不会自动导入运营数据库。

规则管理包含“包裹分类规则”和“异常分类规则”两个页签。默认异常规则以 Fusion 已对接的 `ParcelException.ExceptionType` 为准：`ParcelSpacingViolation`、`TargetChuteAssignmentRejected`、`RoutingTimeout`，并包含唯一的“未知异常”系统兜底；所有已发布规则未命中时归入未知异常，该规则不可修改、删除或复制。后端处理事实投影使用相同协议映射和 `Unknown=0` 兜底，保留原始编码和报文，已有1至15枚举编号不变。两类规则分别保存在数据库 ManagedDocuments 中，通过乐观版本拒绝并发覆盖。自定义异常可使用重量、体积、长宽高的数值比较与单位换算，以及条码、Provider 名称、响应正文的多内容文本匹配，支持“且 / 或”组合。页面提供“验证草稿”及已发布规则分类验证，缺失测量不按 0 比较。异常草稿保存后可发布，真实处理事实会应用已发布条件并标记异常。包裹分类规则可保存草稿，当前服务未实现格口调度动作，因此禁止发布包裹分类规则及不支持的执行动作。详见[分拣机异常分类规则](../分拣机异常分类规则.md)。

## 真实接口与能力边界

| 页面 | 后端能力 |
| --- | --- |
| 账号与权限、登录 | 内置账号、角色权限、初始化、真实 Cookie 会话、停用及重置 |
| 规则管理 | 数据库保存、并发保护、包裹类型及异常规则发布，实际处理记录按字段、单位、范围及顺序匹配 |
| 请求审计、慢查询、健康检查 | 服务端查询与详情；503 保留真实不健康报告 |
| 备份与恢复 | MySQL 事务快照、持久化文件、受认证下载、新隔离数据库恢复及逐表行数核验 |
| 分区管理 | 真实目录及包裹主表、关联表预建；重复执行幂等，审计日表仍属单独规划 |
| 系统配置 | 自动备份、备份间隔和预建窗口在线持久化；其他安全的部署参数只读 |

初始化与设备接口鉴权见 [部署说明](../deploy/README.md)。Windows 原生发布执行 `../deploy/publish-windows.ps1`，前端自动打包到 Host 的 `wwwroot`，页面和 API 使用同一程序、同一端口；目标机无需单独部署此 Web 项目。普通 `dotnet publish` 同样默认包含前端。
