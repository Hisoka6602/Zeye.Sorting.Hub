# 数据访问规范

项目优先使用 EF Core LINQ 表达关系数据库的业务查询，使用 `SaveChanges`、`ExecuteUpdate`、`ExecuteDelete` 执行业务写入。能在数据库端翻译的筛选、投影、排序、分页和聚合，不新增手写 SQL 或 ADO.NET 业务查询。

## 业务查询

- 只读查询使用 `AsNoTracking`，通过 `Select` 读取需要的字段。
- 将筛选、排序、分页和聚合放在 `ToListAsync` 等执行操作之前，并传递取消令牌。
- 不为避免 SQL 而先加载全部明细，或使用 `AsEnumerable` 将大规模聚合转移到应用内存。
- 批量修改优先使用 `ExecuteUpdate`、`ExecuteDelete`；需要领域处理或并发令牌时保留实体跟踪和 `SaveChanges`。
- 标量跨分表读取优先使用 `ParcelPartitionReadContext<TReadModel>`，以 LINQ 合并物理表；统计先在各表聚合，再合并少量结果。
- 分表裁剪依据实际查询时间与分表锚点的关系。处理事实的 `OccurredAt` 可与 `PartitionTime` 跨周期，不能直接按发生时间省略历史分表。
- 优化查询时验证实际生成的查询、索引和结果口径，避免用 LINQ 写法替代执行计划验证。

## 原生 SQL 的有限适用范围

仅在提供器或 EF Core 当前能力无法合理表达需求时保留原生 SQL，并集中在基础设施适配器中。业务服务继续使用 LINQ，不直接拼接数据库语句。

| 位置 | 保留原因 |
| --- | --- |
| EF Core 迁移、数据库方言、分表维护 | 建库、DDL、系统目录和数据库锁具有提供器专属语法。 |
| 备份恢复、连接会话初始化、自动调优 | 原生备份、会话参数、执行计划和索引维护属于数据库管理能力。 |
| `ParcelPartitionQueryBuilder` | 合并动态物理表的完整实体查询根，保留既有聚合映射。上层筛选、排序、分页、投影和聚合继续由 LINQ 生成。 |
| `ParcelCreationIntervalQuery` | 相邻时间间隔和准确中位数依赖 `LAG`、`ROW_NUMBER` 等窗口函数。当前 EF Core 9 没有通用 LINQ 窗口函数 API；不能以下载全部包裹或反复扫描明细替代。 |
| `ConfigurationHistoryStore` 初始化 | 保持版本一历史文件的既有九列结构、WAL 和 SQLite 版本标记。插入、读取、状态更新和恢复检查使用 EF Core。 |

EF Core 窗口函数支持的跟踪事项见 [dotnet/efcore #12747](https://github.com/dotnet/efcore/issues/12747)。升级提供器或重构映射后，应重新评估这些例外。

保留的原生 SQL 中，值必须参数化；表名、列名只能来自 EF 模型和校验后的物理分表目录，并使用提供器的标识符转义。禁止拼接请求中的 SQL、表名或排序表达式。

## 当前优化

处理事件统计在每个物理分表按可空成功状态进行一次 LINQ 聚合，总事件数、失败次数、未绑定 DWS 次数共用同一次发生时间范围检索。每表最多返回成功、失败和未知三组，再合并小结果；不使用三个独立标量计数或外层 `Take(1)`，保留全部历史分表中的晚到事实。允许数据库为三组进行有界分组，性能检查应关注实际物理表读取次数与时间范围覆盖索引，不以查询中完全没有 `GROUP BY` 为目标。配置历史使用独立 EF Core 上下文，兼容原始 JSON、版本、提交状态和同毫秒记录的插入顺序。

耗时分析的处理事实按所选总体的包裹编号逐表读取，每批最多 512 个编号，利用已有 `ParcelId` 索引筛选。阶段、时间和来源条件在数据库中执行，避免先构造包含报文的跨分表 `UNION` 集合。所有批次及历史基础表都参与统计，晚到响应仍按首次入库锚点归组；阶段耗时不读取诊断报文，接口分类只读取有界元数据。

耗时分析覆盖索引 `IX_Processing_Stage_PartitionTime_Duration` 的基础表迁移和历史分表补建继续使用 EF Core 模型及迁移生成器。MySQL 运行期和设计时生成器要求 `ALGORITHM=INPLACE LOCK=NONE`，不支持时保留错误并阻断，禁止自动退回阻塞业务写入的算法。其他索引及数据库提供器保留原有生成方式。在线 DDL 仍需要读取数据并可能等待元数据锁，不能保证建索引瞬间完成，参见 [MySQL 在线 DDL 限制](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-limitations.html)。

`CREATE INDEX` 属于结构维护。历史分表索引按版本和真实索引目录跳过已完成的操作，缺失索引只补建一次；不因它出现在慢查询画像中而删除索引、提高慢查询阈值或过滤维护失败。成功耗时及超时、错误证据继续保留。首次覆盖索引构建耗时与业务 `SELECT` 延迟分开评估，业务优化仍以实际执行计划和重复测量为准。

查询改动至少验证受支持提供器的翻译，以及时间边界、空结果、可空字段和跨分表数据的业务结果；性能结论以对应数据库的执行计划和测量为准。
