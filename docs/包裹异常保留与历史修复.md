# 包裹异常保留与历史修复

包裹的“已完成”表示设备确认实际落格，不表示处理过程没有异常。`Status` 保存生命周期，`ExceptionType` 保存处理质量；完成后继续保留异常分类。概览、工作台、异常分析均按异常分类计数，同一票只计一次，完成票数和异常票数可以重叠。

正常落格要求目标和实际格口均有值且表示同一格口，且不采用兜底或强排格口。数字编号按数值比较（邮政目标 `0001` 与实际 `1` 相同）；非数字编码去除首尾空格并忽略大小写比较。无效编号、目标实际不一致、兜底或路由阻断记为“异常落格”；已经记录的无信息、超时等具体异常优先保留。正常落格不清除先前异常。格口分析中的“编码不一致”保留原始编码比较口径，不等同于异常票数。

Fusion 的新版本将实际落入 `DataFusion:FallbackChuteCode` 的包裹明确上报为兜底，即使 Provider 返回了相同的目标格口。配置仍在 Fusion 维护，Hub 不硬编码现场格口号。Hub 与 Fusion 均需更新相应构建。

## 已有数据恢复

旧版已经清空的异常类型不能通过刷新页面恢复。`tools/ParcelExceptionRepair` 复用新分类逻辑读取完整历史，补回异常分类与质量标记，保留原始事实、去重凭据、实际格口和完成时间。工具面向当前 SQLite 部署，其他数据库会明确拒绝执行；单次范围最多31天。

先发布工具，或在源码目录运行：

```bat
dotnet publish tools\ParcelExceptionRepair\ParcelExceptionRepair.csproj -c Release -r win-x64 --self-contained false -o artifacts\parcel-exception-repair
```

以下示例假设 Hub 部署目录为 `D:\Sorting.Hub`。工具从该目录读取实际 LiteDB 配置、业务数据库路径及已发布规则，不使用源码默认配置覆盖现场配置。

预览（不修改业务库）：

```bat
ParcelExceptionRepair.exe --config-root D:\Sorting.Hub --from 2026-10-16 --to 2026-10-16 --output D:\Sorting.Hub\exception-preview
```

停止 Sorting.Hub 后执行修复，并使用新的输出目录：

```bat
ParcelExceptionRepair.exe --config-root D:\Sorting.Hub --from 2026-10-16 --to 2026-10-16 --apply --confirm-stopped --output D:\Sorting.Hub\exception-repair
```

每票修改前将原值与目标值落盘到 `applied.jsonl`。条件更新复核原值；发生并发修改会停止，已成功部分可以重复执行。修复完成后启动新版本 Hub，检查已完成包裹仍有异常分类、概览与异常分析的计数一致。无需重新过机或删除发送库。

需要撤销本次修复时，停止 Hub 后运行：

```bat
ParcelExceptionRepair.exe --config-root D:\Sorting.Hub --rollback D:\Sorting.Hub\exception-repair\applied.jsonl --confirm-stopped --output D:\Sorting.Hub\exception-rollback
```

回滚只修改审计中记录的质量字段，并要求数据库路径及当前值仍与修复结果一致；后续已变化的记录不会被覆盖。若历史事实本身已按保留策略清理，工具无法恢复缺失的证据；未曾上报的兜底格口配置也不会被猜测。
