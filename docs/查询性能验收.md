# 查询性能验收（2026-10-08）

本次修复并实测 MySQL、SQL Server、Oracle、SQLite 的报表、耗时分析、DWS 一致性、时序、对比、条码检索、列表分页、详情、邻近包裹和审计列表。四库使用相同业务代码和 EF Core 查询，没有用关闭采集、清空历史或缓存命中代替查询优化。

## 已修复的瓶颈

- 耗时接口先按所选业务类型裁剪调用投影，扫描上传、请求格口、落格回传、图片和其他接口分别缓存，强制刷新读取真实数据。历史宽报文的归并由后台执行，新增、迟到和未完成投影仍有有界回退，避免统计遗漏。
- 阶段查询只读取时间端点、来源身份和可靠性，避免搬运报文大字段。先以 EF 的阶段等值分支与 `Concat` 裁剪读取，再增加来源、阶段、固定分表时间和端点的 `IX_Processing_Source_Stage_Duration` 覆盖索引。保留无来源筛选的旧阶段索引，不增加手写业务 SQL 或索引提示。四库各有独立 EF 迁移，历史事实分表由启动维护自动补齐；每库确认五张物理事实表已有新索引。
- 时序、对比和邻近包裹改用只读标量投影，编号、条码、邻近范围和每分表取数上限在合并前执行，避免先物化宽表再筛选。
- 跨分表的深分页和游标查询复用标量读模型，将过滤和每分表游标上限下推；保持全局排序、分页总数、锚点排除和同条码不同包裹的行为。

- 处理事实总量、失败及未关联 DWS 以常量分组和条件聚合一次扫描统计，避免按成功标记排序分组。DWS 单次有效测量直接生成指标，来源统计复用已计算结果；缺失、负值、真实零值及明确参考值保持原语义。

- 大总体查询按完整毫秒的半开时间范围分窗，普通事实目标 4,096 行，DWS 测量和检测目标 8,192 行。通过 EF 按分表时间排序查找下一窗口边界，避免递归计数反复扫描大范围，结果直接枚举原 EF 查询；密集同毫秒仍读取全部记录，不以截断、采样或减少总体获取通过。稀疏七日总体只需八次命令，边界探测不执行 `COUNT`。
- DWS 测量新增 `IX_Dws_Time_Stage_Success`，覆盖时间边界读取；保留原有来源读取索引。四库各有独立 EF 迁移，启动时自动补齐历史物理分表。MySQL 使用已有在线索引迁移生成器，验收仅纯读取核对启动后的索引。
- 耗时阶段分别使用阶段等值的时间索引窗口，避免多阶段条件或合并之后排序重复扫描剩余日期范围。完整阶段记录仍按来源身份合并，跨日端点、真实零值及密集同毫秒数据保持原有统计结果。
- Oracle 阶段查询只选择十个必要字段，移除八个无用的空值投影；专属查询拦截器按驱动 `RowSize` 将取数批次设置为目标 1,024 行，额外内存上限 2 MiB，保持显式更大配置。只作用于 EF LINQ 读取，不改动 SQL、写入或 LOB 模式。DWS 源身份仅解析一次，无缺失条码时跳过身份分组；度量冲突检测使用单次比较，减少每组哈希集合分配。

来源实例、会话及设备包裹号仍须完整匹配。真实零耗时、未知和不可靠时间、跨日端点、重试和调用去重的语义保持不变。历史分表与新增读模型遵循现有四库 EF 迁移和自动维护机制；设备接收热路径没有增加文件读写或投影查询。

## 2026-10-30 慢查询主动检查及程序更新自动迁移

本轮在Windows隔离MySQL 8.0.46实例（仅监听127.0.0.1:34079）使用专属数据库 `zeye_bench_slow_audit`。复用验收工具的真实读服务场景，固定20,000票、180,000条事实、20,000条审计，跨2026-09-09至2026-10-08两个月分表及基础表；每条事实带约2 KiB报文。检查22类查询，另测工作台24小时统计。完整报表和DWS均强制刷新，每项首次调用与两次稳态分开记录。

### 复现、修改与结果

| 路径 | 发现的问题 | 修复 |
| --- | --- | --- |
| 完成耗时、分析报表 | MySQL仍可能对每票端点选择单独的发生时间索引，反复读取宽事实 | 检测和完成分别核对，不可靠端点使用含事实主键的窄集合，保持完整身份和同刻首检测、末成功完成规则 |
| DWS一致性历史关联 | 已补齐窄表仍回查原事实，并把初始窗口内消息重复读取 | 已补齐周期使用耐久窄表，增加消息、阶段和成功状态索引；只补查窗外的历史接收及后续冲突 |
| DWS未补齐回退 | 混合阶段查询及来源索引导致十几万条宽事实反复回表 | 接收、绑定分别按阶段和时间读取有界主键，再以500主键批量取量测字段；检测增加包裹、阶段、身份和端点覆盖索引 |
| DWS来源展示 | 同一来源的多个工作台名称依赖无序查询的首行 | 使用序数最小的非空名称，使事实回退和窄表返回相同来源展示 |

## 2026-10-30 DWS一致性及历史回退第二轮优化

### 实现与正确性

- 历史核对先用来源、时间、阶段及成功状态覆盖索引执行存在性探测，只对确有窗外事实的周期读取消息。更早的接收、晚到绑定和后续冲突继续参与原有完整身份核验。
- 未补齐周期先从原事实读取有界主键，确定完整查询总体；再读取实际已存在的窄投影，仅对缺失主键回读原事实。缺失集合在应用中固定，后台在窄表读取之后补入记录也不会使原事实被错误跳过。
- 主键按序处理。MySQL数字包裹编号每批最多2,048个、窄表字符串主键1,024个、宽事实字符串主键256个；其他提供器保留500个的兼容批次。宽事实最多四条独立连接读取，合计物化不超过1,024条；外部显式共享连接保持串行。
- 调整批次的依据是实际执行计划：把宽事实字符串主键扩大到2,048个时，MySQL报告3170警告，超出8 MiB范围优化预算并放弃主键范围检索。该失败版本及计划单独保留，正式代码使用小批次，并通过独立上下文重叠读取。
- 新增原事实及DWS窄表的 `SourceInstanceId / PartitionTime / Stage / IsSuccess` 覆盖索引，分别由 `AddDwsSourceWindowIndexes` 四库迁移创建；原有三个索引继续保留。

### 启动保护与自动升级

在线DDL生成范围原先只包含上一批三个分析索引，本轮补齐现场五个新索引及新的端点覆盖索引。运行期与设计时生成的目标DDL均要求 `ALGORITHM=INPLACE LOCK=NONE`，在隔离MySQL上实际执行通过。该选项允许符合条件的普通二级索引在线创建，但仍有一次性构建成本和开始、结束阶段的元数据锁，不能承诺零等待或瞬间完成，见[MySQL在线DDL操作](https://dev.mysql.com/doc/refman/8.0/en/innodb-online-ddl-operations.html)及[限制](https://dev.mysql.com/doc/refman/8.0/en/innodb-online-ddl-limitations.html)。不能由旧DDL没有显式选项反推现场曾阻塞写入。
