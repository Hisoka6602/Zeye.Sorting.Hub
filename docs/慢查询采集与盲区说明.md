# 慢查询采集与盲区说明

## 为什么接口很慢，SQL 页面却没有记录

请求审计统计整个接口的耗时。原来的 SQL 拦截器只统计执行命令到返回读取器的时间，后续读取结果、EF 物化、连接等待、多次查询及应用处理可能使接口达到十几秒，却没有任何单条命令超过慢查询阈值。EF 的 `ReaderExecuted` 并不代表全部结果已经消费完毕。[EF Core 官方说明](https://learn.microsoft.com/en-us/dotnet/api/microsoft.entityframeworkcore.diagnostics.idbcommandinterceptor.readerexecutedasync?view=efcore-9.0)

此外，进程重启会清空原来的内存样本；观测窗口过期、容量淘汰、TopN 截断和缓存的空列表也可能让记录不可见。

本次把 SQL、连接、事务和请求分开观测，通过 TraceId 关联。接口慢不再自动等同于 SQL 执行慢。

## 已覆盖的路径

| 原有盲区 | 当前采集方式 |
| --- | --- |
| 返回第一行很快，后续行读取很慢 | 包装读取器，统计同步和异步 Read、NextResult，直到关闭或释放 |
| 大字段、流和文本读取很慢 | 统计字段获取、GetBytes、GetChars、Stream 和 TextReader 的读取及释放 |
| EF 物化、应用消费和等待 | 从读取器存续时间中区分提供器读取与消费时间 |
| 读取期间失败、超时或取消 | 在实际失败处发布，原异常继续传播，后续释放不重复采集 |
| 提前停止读取 | 标记提前结束，保留实际已读行数，不冒充完整读取 |
| 连接池等待、网络建连失败 | 通过连接拦截器单独记录连接打开耗时和异常 |
| 提交、回滚和保存点很慢 | 记录事务动作耗时，不把事务从创建到释放的生命周期算成等待 |
| 多条短 SQL 累计很慢 | 请求内累计所有已完成命令的数量、数据库耗时、连接耗时和读取行数 |
| 接口慢但没有执行 SQL | 记录 HTTP API 请求总耗时，包括缓存等待、应用处理及响应生成 |
| HTTP 500 或未处理异常 | 即使低于慢阈值也采集，保留响应状态和异常类型 |
| 请求审计被关闭、排除或抽样 | 慢查询观测独立于请求审计的正文采样和开关 |
| SignalR 调用 | Fusion 单次调用由 HubFilter 记录；网页查询通过原有端点调度中间件计量 |
| 主库、只读库及物理分表 | 统一注册执行、连接和事务拦截器；分表上下文继承模板选项 |
| 原生元数据、会话设置和备份命令 | 现有必要 ADO 命令经过统一计量入口，保留原事务及顺序读取行为 |
| 配置历史 SQLite | DI 建立后接入诊断，按 configuration 用途分组 |
| 超时、死锁被包装或混淆 | 展开包装异常；区分 MySQL 1205 锁等待超时与 SQL Server 1205 死锁；取消独立计数 |
| 长 SQL 前缀相同、参数变化造成指纹误差 | 按完整归一化结构及类别、提供器、用途生成指纹，再裁剪展示文本 |
| TopN 隐藏、空列表缓存 | 列表返回容量范围内全部指纹，去除诊断端点输出缓存 |
| 重启丢失 | 后台 EF SQLite 批量归档，重启恢复仍在有效窗口内的样本 |
| 已开始但未完成、采集故障或容量丢失 | 返回进行中的数据库操作、最久耗时、TraceId、过期及淘汰计数、采集失败和归档状态 |

同步和异步路径均保留原始返回结果、异常和取消语义。读取器只发布一次观测。仅消费慢、连接慢、事务慢、请求慢及辅助库观测不能触发业务库自动创建索引。

## 时间与数量口径

- SQL 总耗时是命令执行至读取器返回的时间，加上读取器存续时间。执行、实际读取和消费三部分分别展示。
- 消费时间包括 EF 物化、应用处理及读取之间的等待，不代表数据库服务器执行时间，也不能据此直接判定索引问题。
- 请求总耗时是请求墙钟时间。数据库累计耗时包含各命令执行、实际读取及事务动作；并行查询时可能超过请求总时长，不能直接相减计算应用耗时。
- 连接等待另列；实际读取行数和受影响行数分开；事务动作不增加 SQL 命令数。
- “采集样本数”和 P95/P99 仅针对被采集且仍保留的慢、失败或取消样本，不是所有查询次数及全量请求分位数。
- SQL 只保存脱敏结构，不读取参数值或连接字符串；请求只记录路由模板或 SignalR 方法名，不记录正文、方法参数及业务编号。异常仅保存类型。

## 默认配置与保存位置

配置位于 `Zeye.Sorting.Hub.Infrastructure/Configuration/default-settings.json` 的 `Persistence:AutoTuning`：

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| SlowQueryThresholdMilliseconds | 500 | 正常完成的慢观测阈值，失败与取消不受阈值过滤 |
| SlowQueryProfile:IsEnabled | true | 画像采集开关 |
| SlowQueryProfile:WindowMinutes | 30 | 页面有效观测窗口 |
| SlowQueryProfile:MaxFingerprintCount | 1000 | 内存指纹上限 |
| SlowQueryProfile:MaxSampleCountPerFingerprint | 256 | 每个指纹的内存样本上限 |
| SlowQueryProfile:ArchiveEnabled | true | 后台归档及启动恢复 |
| SlowQueryProfile:ArchiveDirectory | governance-artifacts/slow-queries | 相对 Host 内容目录的归档目录 |
| SlowQueryProfile:ArchiveRetentionDays | 7 | 归档保留天数 |
| SlowQueryProfile:ArchiveMaximumSamples | 50000 | 归档样本数量上限 |

归档文件为 `<Host内容目录>/governance-artifacts/slow-queries/observations.db`。现有 Docker 部署的治理目录挂载可保留该文件。后台通过 EF Core 读写，热路径仅访问内存和有界队列，不同步访问文件或诊断数据库。

`TopN` 保留为旧配置兼容字段，不再截断诊断页面。内存容量仍然受上述上限控制，超过时显示淘汰数量。归档队列上限为 4096，满队列立即计数而不等待业务请求。

## 排查空列表

1. 查看页面采集开关、阈值及窗口；重置类别、指纹和最小耗时等筛选。
2. 查看进行中的数据库操作。查询未完成或读取器未释放时，完整样本尚未发布。
3. 接口总耗时高时选择“请求累计”，按最近 TraceId 对照请求审计及相关 SQL。
4. 读取耗时高优先排查返回行数、字段大小和网络；消费耗时高检查物化和应用处理；连接等待高检查连接池及数据库可用性。
5. 查看容量淘汰、正常过期、采集失败、归档待写和丢失计数；不要将空列表解释为系统一定没有性能问题。

## 明确边界

- 部署前已经发生且没有 SQL 观测的请求，无法从请求耗时反推出历史 SQL；只能保留原请求审计并在新版本下复现定位。
- 页面当前展示有效窗口；七天归档用于保留及启动恢复，尚未提供跨窗口历史检索页面。
- 正常停止会尽力排空归档队列，已测试初始化未完成就停止的场景。强制终止、断电或持续存储失败仍可能丢失未落盘样本；不能承诺绝对零丢失。
- EF Core 不提供事务开始失败拦截事件，失败由请求或连接观测记录，无法单独还原失败 BEGIN 的精确耗时；原生备份事务入口可以单独记录开始失败。
- DI 建立前的配置历史引导、设计时迁移工具，以及未经过本项目计量入口的外部数据库操作，不在运行时画像内。归档数据库自身不接入采集，以防诊断递归。
- 长连接和订阅生命周期不算单次慢请求；应用后台任务没有 HTTP 请求汇总，但其 EF 命令、读取、连接和事务动作仍按数据库观测采集。
- 实际运行中的采集阈值和窗口以页面返回状态为准；这些启动配置更改需要重新启动 Host。

## 验证范围

`SlowQueryDiagnosticsCoverageTests` 使用独立 SQLite 和临时归档验证真实流式读取、读后失败、取消、大字段、请求累计、HTTP 状态、SignalR 单次调用、事务和保存点、原生命令、配置历史、脱敏、指纹区分、容量背压、归档恢复、损坏记录、轮转和早停排空。

本次回归包含现有自动调优、四数据库提供器注册、迁移治理、备份、请求审计、SignalR、查询治理及分表维护测试；前端执行类型检查与现有测试。注册及模型测试不等于四种真实数据库服务的端到端压测。
